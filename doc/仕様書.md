# NoteHub 実装仕様書

## 1. システム概要

### 1.1 基本情報

  ---------------------------------------------------------------------------------------------------------------------------------
  項目           内容
  -------------- ------------------------------------------------------------------------------------------------------------------
  システム名     NoteHub

  システム種別   リアルタイム共同編集オンラインエディタ

  利用対象       チームで共同作業を行うユーザー

  主な機能       ユーザー認証、ワークスペース管理、メンバー管理、ドキュメント管理、リアルタイム共同編集、編集履歴、アカウント管理

  通信方式       REST API、WebSocket

  永続データ     PostgreSQL

  一時データ     Redis
  ---------------------------------------------------------------------------------------------------------------------------------

### 1.2 システム目的

NoteHubは、複数ユーザーが同じドキュメントをリアルタイムで共同編集できる環境を提供する

ワークスペース単位でメンバーとドキュメントを管理し、WebSocketを利用して編集内容を同期する編集中のドキュメント本文はRedisへ一時保存し、自動保存処理によってPostgreSQLへ永続化するDocumentVersionを利用して編集履歴を保持し、過去の状態へ復元できるようにする

悪意あるユーザーに対しては、まずアカウント停止を行い、必要に応じて論理削除する停止または論理削除されたユーザーが他のワークスペースでHostを務めている場合、そのワークスペースも利用不可とする

### 1.3 解決する課題

  ------------------------------------------------------------------------------------------------------------------------
  課題                                      解決方法
  ----------------------------------------- ------------------------------------------------------------------------------
  編集内容が他の利用者へ反映されない        WebSocketでリアルタイム同期する

  編集内容を保存し忘れる                    Redisへの一時保存と自動保存Batchを利用する

  過去の状態へ戻れない                      DocumentVersionへ編集履歴を保存する

  誰が編集中か分からない                    接続中ユーザーを編集者一覧として表示する

  悪意あるユーザーをすぐに排除できない      Hostがアカウント停止を実行できるようにする

  誤ってアカウントを削除する可能性がある    停止と論理削除を段階的に行う

  停止済みHostのWorkspaceが利用され続ける   Hostのアカウント状態からWorkspace利用可否を判定する

  同時更新で保存内容が競合する              Documentのrevisionによるrevisionを比較して同時更新の競合を検出する方式を行う
  ------------------------------------------------------------------------------------------------------------------------

## 2. アーキテクチャ

### 2.1 基本方針

バックエンドはClean Architectureの依存関係を維持する

通常のHTTP APIは次の順序で処理する

``` text
Router
  ↓
Middleware
  ↓
Controller
  ↓
UseCase
  ↓
Repository / Redis用Interface / WebSocket用Interface
  ↓
PostgreSQL / Redis / WebSocket Hub
```

WebSocketは次の順序を基本とする

``` text
WebSocket Router
  ↓
WebSocket認証
  ↓
WebSocket Controller
  ↓
UseCase
  ↓
Repository / Redis用Interface
  ↓
WebSocket Hub
```

### 2.2 各層の責務

  ----------------------------------------------------------------------------------
  層                   責務
  -------------------- -------------------------------------------------------------
  Router               URLとControllerを関連付け、必要なMiddlewareを適用する

  Middleware           認証、CSRF、CORS、リクエスト回数制限、Request
                       ID、Logging、Recoveryを行う

  Controller           HTTP/WebSocket入力を受け取り、DTOへ変換しUseCaseを呼び出す

  UseCase              業務処理、認可、状態確認、Transaction、処理順序を管理する

  AuthService          Password、JWT、RandomToken、Tokenハッシュ値、Access
                       Token失効、Login失敗管理を認証UseCaseへ提供する

  Repository           PostgreSQLへのデータアクセスを行う

  Redis                Token管理、リクエスト回数制限、Document
                       Cache、未保存管理、編集者一覧、WebSocket
                       Session、排他制御等を管理する

  WebSocket            接続管理、イベント受信、配信、強制切断を行う

  batch                自動保存、Document
                       未保存内容をPostgreSQLへ保存、Backup、Cleanupを定期実行する

  Entity               DB Entity、状態、ドメイン定数、状態遷移を定義する

  DTO                  API Request/Response、WebSocket Eventの入出力形式を定義する

  Config               環境変数とアプリケーション設定を管理する

  Crypto               JWT、bcrypt、Token生成、ハッシュ値処理を行う
  ----------------------------------------------------------------------------------

### 2.3 Routerの実装方針

Routerは以下のみを担当する

-   REST APIまたはWebSocket URLとControllerを関連付ける
-   認証、CSRF、リクエスト回数制限等のMiddlewareをルート単位で適用する
-   公開APIと認証必須APIを分離する

Routerでは業務ロジック、DBアクセス、Redisアクセス、通常レスポンス生成を行わない

### 2.4 Middlewareの実装方針

  Middleware            処理
  --------------------- ----------------------------------------------------------------------
  AuthMiddleware        Access Tokenを検証し認証情報をリクエスト内の共有情報へ保存する
  CSRFMiddleware        CSRF CookieとX-CSRF-Tokenを照合する
  CORSMiddleware        許可Originのみ通信を許可する
  RateLimitMiddleware   一定時間ごとに利用可能回数を補充する方式方式でリクエスト数を制限する
  RequestIDMiddleware   リクエストごとにRequest IDを付与する
  LoggingMiddleware     Method、Path、Status、処理時間等を記録する
  RecoveryMiddleware    Panicを捕捉し500へ変換する

### 2.5 Controllerの実装方針

Controllerは以下を担当する

1.  Path Parameterを取得する
2.  Query Parameterを取得する
3.  Request BodyをDTOへ変換する
4.  入力値を検証する
5.  認証済みUser情報をリクエスト内の共有情報から取得する
6.  UseCaseを呼び出す
7.  UseCase結果をResponse DTOへ変換する
8.  UseCase ErrorをHTTP StatusとErrorCodeへ変換する

ControllerではRepository/Redisへの直接アクセス、業務条件判定、Transaction開始、bcrypt/JWTの直接操作を行わない

### 2.6 UseCaseの実装方針

UseCaseは業務処理の実行順序と各処理の呼び出しを一元管理する

基本処理順序は以下とする

1.  入力値を検証する
2.  実行ユーザーを取得する
3.  実行ユーザーの状態を確認する
4.  対象データを取得する
5.  Workspace所属を確認する
6.  Role・操作権限を確認する
7.  業務条件を確認する
8.  必要に応じてTransactionを開始する
9.  DBを更新する
10. AuditLogを保存する
11. TransactionをCOMMITする
12. Redisを更新する
13. WebSocket通知または切断を行う
14. 処理結果を返す

DB
COMMITが失敗した場合はWebSocket通知を行わないCOMMIT後のWebSocket通知失敗ではDBをRollbackしないRedis更新失敗はログへ記録し、処理ごとの復旧方針に従う

### 2.7 Repositoryの実装方針

RepositoryはPostgreSQL操作のみを担当する

-   GORMでCRUDを実行する
-   UseCaseから渡されたTransactionを利用する
-   必要な処理では行ロックを利用する
-   DBエラーをRepository共通Errorへ変換する
-   業務条件判定、HTTP処理、DTO生成、WebSocket通知を行わない

### 4.2 起動時検証

起動時に以下を検証し、不正な設定では起動を失敗させる

-   HTTP_PORTが1〜65535である
-   DATABASE_URLが存在し、接続文字列として妥当である
-   JWT_SECRETが存在し、32byte以上である
-   Access Token / Refresh Token TTLが正の値である
-   BCRYPT_COSTが10〜16である
-   COOKIE_SAME_SITEが許可値である
-   REDIS_OPERATION_TIMEOUTが0〜30秒の範囲である
-   Rate
    Limit、WebSocket接続上限、自動保存、Cleanup、Backup関連値が妥当である
-   productionではREDIS_URLを必須とする
-   productionではCOOKIE_SECURE=trueとする
-   productionではCORS_ALLOWED_ORIGINSを必須とし、`*`を禁止し、HTTPS
    Originのみ許可する

## 5. Entity仕様

### 5.1 User

  ----------------------------------------------------------------------
  フィールド       DB型             制約             内容
  ---------------- ---------------- ---------------- -------------------
  id               UUID             PK               User ID

  email            VARCHAR(255)     NOT NULL         Email

  password_hash    VARCHAR(255)     NOT NULL         bcrypt ハッシュ値

  name             VARCHAR(100)     NOT NULL         表示名

  status           VARCHAR(20)      NOT NULL, INDEX  active / suspended
                                                     / deleted

  auth_version     INTEGER          NOT NULL,        Access
                                    default 1        Token一括失効判定

  suspended_at     TIMESTAMPTZ      NULL可, INDEX    停止日時

  deleted_at       TIMESTAMPTZ      NULL可, INDEX    論理削除日時

  created_at       TIMESTAMPTZ      NOT NULL         作成日時

  updated_at       TIMESTAMPTZ      NOT NULL         更新日時
  ----------------------------------------------------------------------

Emailは`LOWER(email)`かつ`deleted_at IS NULL`を条件とする部分ユニークインデックスで重複を防止する論理削除時は認証情報を利用不可とし、同一Emailでの再登録を可能にする

状態遷移は以下とする

``` text
active
  ├─ Suspend() ─────→ suspended
  └─ LogicalDelete() → deleted

suspended
  ├─ Reactivate() ───→ active
  └─ LogicalDelete() → deleted

deleted
  └─ 復帰不可
```

Suspend、Reactivate、LogicalDeleteでは`auth_version`をインクリメントし、既存Access
Tokenを無効化する

`CanAuthenticate()`はstatusがactiveかつdeleted_atがNULLの場合のみtrueとする

## 6. Migration仕様

DB Schemaの生成は`db.Migrate()`からGORM
AutoMigrateを実行するEntityで表現しにくい部分ユニーク制約や複合Index等は補助SQLで作成する

主要Indexは以下を含む

``` sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_users_email_active
ON users (LOWER(email))
WHERE deleted_at IS NULL;

CREATE INDEX IF NOT EXISTS idx_users_status
ON users (status);

CREATE UNIQUE INDEX IF NOT EXISTS uq_refresh_tokens_hash
ON refresh_tokens (token_hash);

CREATE INDEX IF NOT EXISTS idx_refresh_tokens_family_status
ON refresh_tokens (family_id, status);

CREATE INDEX IF NOT EXISTS idx_refresh_tokens_user_status
ON refresh_tokens (user_id, status);
```

documents、document_versions、audit_logs等にも検索条件に対応するIndexを設定する

## 8. 認証・認可仕様

### 8.1 Password

-   Passwordはbcryptでハッシュ値化して保存する
-   平文PasswordはDB・ログへ保存しない
-   Login時は入力Passwordと保存済みハッシュ値をbcryptで照合する

### 8.2 Access Token

  項目               内容
  ------------------ ---------------------------------------
  形式               JWT
  署名アルゴリズム   HS256
  有効期限           既定15分
  クライアント保存   ブラウザメモリ
  LocalStorage       保存禁止
  SessionStorage     保存禁止
  Cookie             保存しない
  DB                 保存しない
  送信               `Authorization: Bearer {AccessToken}`

JWT JWT内の認証情報:

  JWT内の項   目 内容
  ----------- --------------------
  iss         Token発行者
  aud         Token利用対象
  sub         User ID
  jti         Access Token固有ID
  iat         発行日時
  exp         有効期限
  ver         User.auth_version

TokenへEmail、Password ハッシュ値、User.status、Workspace
Role、Workspace一覧、Document権限を含めない

### 8.3 AuthMiddleware処理

1.  Authorization Headerを取得する
2.  Bearer形式を確認する
3.  JWTをParseする
4.  HS256であることを確認する
5.  JWT_SECRETで署名を検証する
6.  issを検証する
7.  audを検証する
8.  expを検証する
9.  subからUser IDを取得する
10. jtiを取得する
11. verを取得する
12. Redisでjtiが失効済みでないことを確認する
13. UserをDBから取得する
14. User.statusがactiveであることを確認する
15. JWT verとUser.auth_versionが一致することを確認する
16. 認証情報をリクエスト内の共有情報へ保存する
17. 次のHandlerへ進む

リクエスト内の共有情報には少なくとも`auth_user`、`user_id`、`access_token_jti`、`access_token_exp`、`auth_version`を保持する

### 8.4 Refresh Token

Refresh Tokenは暗号学的に安全な乱数で生成するDBにはSHA-256
ハッシュ値のみ保存し、平文TokenはHttpOnly Cookieでクライアントへ送信する

Refresh TokenはRefresh Tokenを使用するたびに新しいRefresh
Tokenへ更新する方式とする

``` text
Token A(active)
  ↓ refresh
Token A(rotated) ── replaced_by_id ──→ Token B(active)
                                      ↓ refresh
                                 Token B(rotated)
                                      ↓
                                 Token C(active)
```

同じfamily_idをRefresh Tokenを更新して引き継いだ一連のTokenとして扱う

#### 正常Refresh

1.  CookieからRefresh Tokenを取得する
2.  SHA-256 ハッシュ値を生成する
3.  token_hashでDB検索する
4.  Userを取得し認証可能状態を確認する
5.  Tokenがactiveで有効期限内であることを確認する
6.  新Refresh Tokenを生成する
7.  新Token ハッシュ値を生成する
8.  同一family_idで新Tokenレコードを作成する
9.  旧Tokenをrotatedへ変更する
10. replaced_by_idへ新Token IDを設定する
11. 新Access Tokenを発行する
12. 新Refresh Token CookieとCSRF Tokenを返す

#### 再利用検知

rotatedまたはrevoked済みTokenが再利用された場合、Refresh
Token再利用と判定する同一family_idのactive
Tokenをすべてrevokedへ変更し、セッションを無効化する

### 8.5 Logout

Logoutでは以下を行う

1.  Access Token認証を確認する
2.  CSRFを検証する
3.  Refresh Token Cookieを取得する
4.  Refresh Tokenを失効させる
5.  必要に応じてFamily単位で失効させる
6.  現在のAccess Token jtiをRedisへ失効登録する
7.  Refresh Token Cookieを削除する
8.  CSRF Cookieを削除する

### 8.6 CSRF

Refresh TokenをCookieで送信するAPIはDouble Submit
Cookie方式でCSRFを検証する

対象:

-   `POST /api/auth/refresh`
-   `POST /api/auth/logout`

CSRF Token仕様:

  項目       内容
  ---------- ------------------------------
  生成       crypto/rand
  乱数長     32byte
  文字列     Base64 URL Safe、Paddingなし
  Cookie名   notehub_csrf_token
  Header名   X-CSRF-Token
  HttpOnly   false
  Secure     productionでtrue
  比較       一定時間比較

CookieとHeaderの両方が存在し、値が一致した場合のみ処理を続行する

### 8.7 Login失敗制限

Login失敗回数はRedisで管理する

-   最大失敗回数: `LOGIN_MAX_FAILURES`、既定5
-   集計期間: `LOGIN_FAILURE_WINDOW`、既定1時間
-   排他制御時間: `LOGIN_LOCK_DURATION`、既定1時間
-   成功Login時は失敗状態をクリアする
-   Redis障害時は認証系の安全性を優先し、実装で定義された認証サービスエラーとして扱う

### 8.8 リクエスト回数制限

一般APIのリクエスト回数制限はRedis
一定時間ごとに利用可能回数を補充する方式方式とする

-   Capacity: `RATE_LIMIT_CAPACITY`
-   Refill: `RATE_LIMIT_REFILL_PER_SECOND`
-   Controller/UseCaseへ到達する前にMiddlewareで判定する

## 13. AccountUseCase仕様

実装ファイル: `usecase/account.go`

### 13.1 基本方針

Account管理はHostが自WorkspaceのMemberに対して行うHost自身を停止・削除対象にしない論理削除済みAccountは復帰できない

### 13.2 SuspendAccount

1.  Workspaceアクセスを確認する
2.  実行UserがHostであることを確認する
3.  対象UserがWorkspace Memberであることを確認する
4.  対象UserがHost自身でないことを確認する
5.  対象Userが削除済みでないことを確認する
6.  Transaction内でUserをsuspendedへ変更する
7.  `suspended_at`を設定する
8.  `auth_version`を増加させる
9.  AuditLogを保存する
10. COMMITする
11. 対象UserのRefresh Tokenを失効させる
12. 対象UserのWebSocket接続へ`account_suspended`を通知し、`ACCOUNT_SUSPENDED`で切断する
13. 対象UserがHostである別Workspaceへ`workspace_host_suspended`を通知し、それらを利用不可として扱う

### 13.3 ReactivateAccount

1.  WorkspaceアクセスとHost権限を確認する
2.  対象UserがWorkspace Memberであることを確認する
3.  自分自身への復帰操作を禁止する
4.  対象Userがsuspendedであることを確認する
5.  Transaction内でstatusをactiveへ戻す
6.  suspended_atをクリアする
7.  auth_versionを増加させる
8.  AuditLogを保存する
9.  COMMITする

復帰後も既存Tokenは再利用せず、再Loginを必要とする

### 13.4 DeleteAccount

Account削除は論理削除とする

1.  WorkspaceアクセスとHost権限を確認する
2.  対象UserがWorkspace Memberであることを確認する
3.  Host自身または実行User自身の削除を禁止する
4.  削除理由を必須とする
5.  Transaction内でUserをdeletedへ変更する
6.  deleted_atを設定する
7.  auth_versionを増加させる
8.  必要な個人情報を匿名化する
9.  AuditLogを保存する
10. COMMITする
11. Refresh Tokenを失効させる
12. `account_deleted`を通知し`ACCOUNT_DELETED`で接続を切断する
13. 対象UserがHostのWorkspaceへ`workspace_host_deleted`を通知し、利用不可とする

### 13.5 Workspace連鎖ロック

Host
Userのstatusがactive以外になった場合、そのHostが所有するすべてのWorkspaceを利用不可とする

Workspace自体を物理削除または自動論理削除するのではなく、アクセス時にHost状態を確認して利用不可判定する

## 15. Document Cache・自動保存仕様

### 15.1 Redis Document Cache

編集中本文はRedisを一時的な作業領域として利用するPostgreSQLを永続データのPostgreSQLとする

Document Cacheは少なくとも以下を管理する

-   Document本文
-   更新User
-   更新日時
-   未保存状態
-   自動保存に必要なrevision/metadata

UseCase側はRedis実装へ直接依存せず、Document Cache用Interfaceを経由する

主要操作:

``` text
GetContent(documentID)
SetContent(documentID, content, updatedBy, updatedAt)
IsDirty(documentID)
保存済みに変更(documentID)
Clear(documentID)
```

### 15.2 未保存管理

WebSocket編集等でRedis本文を更新した場合、Documentを未保存にする

AutoSave成功後に保存済みに変更する保存に失敗した場合は未保存を維持し、次回Batchで再試行できる状態とする

### 15.3 AutoSave

-   実行間隔: `DOCUMENT_AUTOSAVE_INTERVAL`、既定10秒
-   保存対象: 未保存なDocument
-   最終更新から一定時間経過している条件:
    `DOCUMENT_AUTOSAVE_IDLE_DURATION`、既定60秒
-   PostgreSQL保存成功後にDocumentVersion(type=auto_save)を作成する
-   保存競合はrevisionで検出する
-   必要に応じてRedis 排他制御で多重保存を防止する

### 15.4 未保存内容をPostgreSQLへ保存

以下のタイミングでは通常のAutoSave待ちにせず未保存内容をPostgreSQLへ保存を行う

-   Document削除前
-   Workspace削除前
-   Version復元前後で最新編集内容の確定が必要な場合
-   Shutdown等、実装で未保存内容をPostgreSQLへ保存が必要なタイミング

`未保存内容をPostgreSQLへ保存Document`、`未保存内容をPostgreSQLへ保存WorkspaceDocuments`、`未保存内容をPostgreSQLへ保存AllDirty`を用途に応じて使用する

## 17. WebSocket仕様

### 17.1 接続URL

``` text
GET /ws/documents/:documentId
GET /ws/workspaces/:workspaceId
```

Document接続は共同編集用、Workspace接続はDocument一覧やAccount/Workspace関連イベントの購読用とする

### 17.2 認証

WebSocketは接続確立時にAccess Tokenを検証する

検証内容:

-   JWT署名
-   HS256
-   iss
-   aud
-   exp
-   sub
-   jti
-   Redis失効状態
-   User.status
-   auth_version
-   Workspace所属
-   Document接続の場合はDocument所属Workspaceへのアクセス

未認証・利用不可User・所属外Userの接続は拒否する

### 17.3 同時接続上限

同一User・同一Documentの同時接続数を制限する

-   既定: 3
-   設定: `WS_MAX_CONNECTIONS_PER_DOCUMENT`
-   許容設定範囲: 1〜20
-   上限超過時は新規接続を拒否する

WebSocket SessionはRedisで管理し、接続数判定に利用する

### 17.4 Document接続フロー

1.  Access Tokenを検証する
2.  Documentを取得する
3.  Workspaceアクセスを確認する
4.  接続数上限を確認する
5.  WebSocketへUpgradeする
6.  Sessionを登録する
7.  編集者情報を登録する
8.  HubへClientを登録する
9.  `connected`を送信する
10. Redis Cacheがあれば最新本文、なければDB本文を取得する
11. `document_sync`を送信する
12. `editors_sync`を送信する
13. 他Clientへ`editor_joined`を通知する
14. ClientからのEventを受信する
15. 切断時にSession/編集者情報を削除し、`editor_left`を通知する

### 17.5 Event共通形式

WebSocket EventはEvent種別とPayloadを持つJSONとして扱う

概念形式:

``` json
{
  "event": "document_updated",
  "data": {}
}
```

必要に応じてdocument_id、workspace_id、user情報、revision、reason等をdataへ含める

  --------------------------------------------------------------------------------

  -------------------------- --------------- -------------------------------------

### 17.7 document_edit

Clientは編集後本文と期待revisionを送信する

Server側処理:

1.  接続UserとDocumentを確認する
2.  Workspaceアクセスを再確認する
3.  入力サイズ等を検証する
4.  expectedRevisionを確認する
5.  Redis Cacheへ本文を保存する
6.  未保存=trueとする
7.  revisionを進める
8.  更新User/更新日時を保存する
9.  `document_updated`を同一Documentの他Clientへ配信する

### 17.8 編集者一覧

Redis ハッシュ値でDocumentごとの編集者を管理する

-   接続時に追加
-   切断時に削除
-   接続継続中はTTLを更新
-   既定TTLは16分
-   `editors_sync`で現在一覧を送信
-   `editor_joined` / `editor_left`で差分通知

### 17.9 強制切断Reason

``` text
DOCUMENT_DELETED
WORKSPACE_DELETED
ACCOUNT_SUSPENDED
ACCOUNT_DELETED
WORKSPACE_HOST_SUSPENDED
WORKSPACE_HOST_DELETED
MEMBER_REMOVED
```

強制切断対象イベントでは、可能な場合は理由Eventを送信した後に接続を閉じる

### 17.10 再接続

再接続時はDBのみを信用して古い本文へ戻さない

1.  認証と権限を再検証する
2.  Redis Cacheに最新本文があればRedisを取得する
3.  Redisに無ければPostgreSQLを取得する
4.  最新revisionを同期する
5.  編集者一覧を再同期する
6.  Clientは受信した`document_sync`を基準に編集状態を再構築する

### 18.2 Redisの位置付け

Redisは永続データのPostgreSQLにしないRedis消失時でもPostgreSQLの永続データからサービスを復旧できる構成とする

Redisへ保存する情報は主に以下とする

-   Access Token jti失効情報
-   Login失敗回数
-   リクエスト回数制限状態
-   Document編集中本文
-   未保存状態
-   Document編集者一覧
-   WebSocket Session
-   排他制御
-   一時的なCSRF関連情報

### 18.3 排他制御

自動保存、未保存内容をPostgreSQLへ保存等で同一Documentへ多重処理が発生すると整合性が崩れる処理ではRedis
排他制御を利用する排他制御取得失敗時は同一処理を重複実行しない

## 19. Batch仕様

### 19.1 AutoSaveBatch

実行ファイル: `batch/auto_save.go`

実処理: `DocumentAutoSaveUseCase.RunOnce`

処理:

1.  未保存なDocumentを取得する
2.  最終更新から一定時間経過している条件を満たすDocumentを対象にする
3.  Document単位で排他制御を取得する
4.  Redisの最新本文とmetadataを取得する
5.  DB revisionを確認する
6.  PostgreSQLへ保存する
7.  auto_save Versionを作成する
8.  成功時に未保存を解除する
9.  失敗時は未保存を維持しログへ記録する

### 19.2 Document未保存内容をPostgreSQLへ保存Batch

実行ファイル: `batch/document_flush.go`

以下を提供する

-   `未保存内容をPostgreSQLへ保存Document`
-   `未保存内容をPostgreSQLへ保存WorkspaceDocuments`
-   `未保存内容をPostgreSQLへ保存AllDirty`

削除、終了処理等で未保存内容をDBへ確定させるために利用する

### 19.3 BackupBatch

実行ファイル: `batch/backup.go`

-   `BACKUP_ENABLED=true`の場合のみ実行する
-   既定実行間隔は24時間
-   PostgreSQL Backupを外部コマンド（例: pg_dump）で作成する
-   `BACKUP_DIR`へ保存する
-   `BACKUP_RETENTION`を超えたBackupを削除対象とする
-   Backup失敗はログへ記録する

### 19.4 CleanupBatch

実行ファイル: `batch/cleanup.go`

既定実行間隔は1時間

対象:

-   失効済みかつ`REFRESH_TOKEN_RETENTION`を超えたRefresh Token
-   期限切れRedis一時Key
-   不要になったSession/一時状態

大量削除では一度に過剰な件数を削除せず、Batch単位で処理する

## 26. データ整合性・障害時方針

### 26.1 PostgreSQL

PostgreSQLを永続データのPostgreSQLとするRedisは一時データ・高速化・接続状態管理に利用する

### 26.2 DB更新と通知

-   DB COMMIT前に成功通知を送らない
-   COMMIT後の通知失敗でDBをRollbackしない
-   通知失敗はログへ記録する
-   必要な画面は再取得または再接続でDB/Redisの最新状態へ最新状態へ合わせる

### 26.3 Redis障害

Redisが利用できない場合、処理の性質に応じて以下とする

-   認証・リクエスト回数制限等、安全性に直結する処理は安全性を優先して処理を失敗させる
-   一時Cache取得失敗時にDBへ代替処理が可能な読み取りはPostgreSQLを利用する
-   未保存保存等、データ損失につながる処理は成功扱いにせずログ・再試行対象とする

### 26.4 WebSocket障害

WebSocket切断自体でDB内容を変更しない再接続時に認証・所属・Host状態を再検証し、RedisまたはDBから最新状態を同期する

## 28. 実装時の最終ルール

1.  PostgreSQLを永続データのPostgreSQLとする
2.  Redisは一時データ、リクエスト回数制限、Token失効、WebSocket補助に限定する
3.  Controllerに業務ロジックを書かない
4.  Repositoryに業務条件を書かない
5.  UseCaseが処理順序・認可・Transactionを管理する
6.  DB COMMIT後にRedis更新・WebSocket通知を行う
7.  Account停止・削除時は既存TokenとWebSocket接続を無効化する
8.  Hostが利用不可になったWorkspaceは全Memberに対して利用不可とする
9.  Document本文のリアルタイム編集はRedisへ一時保存し、AutoSave/未保存内容をPostgreSQLへ保存でPostgreSQLへ反映する
10. Documentの競合はrevisionで検知する
11. Versionは追加のみとし、復元前後の状態を履歴として残す
12. Access Tokenはブラウザメモリのみへ保存する
13. Refresh TokenはHttpOnly Cookie、DBではハッシュ値のみを保持する
14. Refresh TokenはRefresh Token更新と再利用検知を行う
15. Refresh/LogoutはCSRF検証を必須とする
16. productionではHTTPS/WSS、Secure Cookie、明示的CORS Originを使用する
17. 重要操作はAuditLogへ記録する
18. Error Responseへ内部実装情報・秘密情報を出力しない
19. WebSocket接続時だけでなく、接続後の権限変更にも強制切断で追従する
20. 実装・テスト・API定義は本仕様書の用語、状態、Route、Event名を基準とする
